# Decisions

Where SPEC.md was unclear I chose the simplest option and wrote it here.

## Product direction (from the owner, before Phase 2)

BedBoard is **free open-source software that each hospital installs and runs for itself**, not a portfolio demo. This shapes every later choice: safe defaults, no shared or built-in credentials in a real install, clear errors, and docs written for a hospital IT person. The demo seed is for trying the product only.

## Phase 2

18. **First-run setup wizard (`/setup`).** A new install has no users, so `/login` redirects to `/setup`, where the hospital enters its name and creates the first ADMIN. It only works while there are zero users (checked under a Postgres advisory lock so two requests cannot both win), then redirects to login for good. This is an addition to the spec, needed so a hospital never has to run the demo seed or ship default passwords.
19. **Demo seed vs real install.** The seed (demo logins, `bedboard123`) is only for trying BedBoard. It is skipped if a hospital row exists, so it will not run on top of a real setup. A real hospital should never run it.
20. **Server refuses to start in production with a bad `AUTH_SECRET`** (missing, under 32 characters, or still the `.env.example` sample). Checked at server start (`src/instrumentation.ts`), not at build, so the Docker image still builds without secrets.
21. **Auth.js v5 (`next-auth@beta`), credentials provider, JWT cookie sessions (12 h).** v5 is still tagged beta on npm but is the Auth.js release that supports Next 15 App Router. Login is phone + password. Phone numbers are 10-digit Indian mobiles starting 6-9.
22. **Role is re-read from the database on every API request** (`guard()` in `src/lib/guard.ts`), not trusted from the cookie. Deactivating a user or changing a role takes effect on their next request. Costs one small query per request.
23. **Every API route calls `guard()` first.** A unit test scans `src/app/api` and fails if a route lacks it, except the deliberately public ones (`api/auth`, `api/health`, `api/setup`, `api/public`). Middleware only redirects pages to `/login`; it is not the security boundary.
24. **Login and PIN rate limits are in memory** (10 failed logins per phone and 5 wrong PINs per user per 15 minutes; 20 setup attempts per IP). Fine for a single app container, resets on restart. A limit per phone means someone can lock out a known number for 15 minutes; accepted over IP limits, which are unreliable behind a hospital proxy or shared NAT. Revisit if a hospital runs several app containers.
25. **PIN (Phase 2 = set and verify only).** A user sets a 4-digit PIN on the Profile page (needs their password). `POST /api/me/pin/verify` checks it. The idle lock screen that uses it is Phase 5, as the spec places idle logout there. An admin can reset a PIN.
26. **Passwords:** 8 to 72 characters (bcrypt ignores bytes past 72). The admin sets a starting password; there is no email, so password reset is done by an admin. Hospitals have no shared mail system to rely on.
27. **Admin cannot deactivate or demote themselves**, which also guarantees at least one active admin always exists.
28. **Ward access (`UserWard`) is only stored for NURSE.** Changing a user to another role clears their wards. Helper `canEditWard()` in `src/lib/rbac.ts` is used by Phase 3 ward actions.
29. **Bulk add** `Bed 1 to 30` = prefix + from + to, up to 200 per request. Labels that already exist in the ward are skipped and reported, so re-running is safe. A bed's type can only change while it is FREE or BLOCKED. Beds and wards are never deleted (history and audit rely on them); wards can be deactivated.
30. **Admin API paths:** `GET, POST /api/admin/{wards,beds,users}` and `PATCH /api/admin/{wards,beds,users}/:id`. Passwords and PIN hashes are never returned.
31. **Audit log** now records logins (and failures for known users), setup, and every admin change. The viewer screen is Phase 5.
32. **Security headers** (nosniff, frame deny, referrer, permissions) set in `next.config.ts`. A Content-Security-Policy is deferred to Phase 7 polish because Next.js inline scripts need a nonce setup.
33. **Hindi strings** are still inline English. Extraction to `messages/*.json` happens in Phase 6 as planned.
34. **Dashboard** is a placeholder after login (real one is Phase 4).

## Phase 5

60. **Midnight census** runs in the worker at 00:00 in the hospital's time zone (read once at worker start; default Asia/Kolkata) and is labelled with the local date that is starting. It counts active wards only, per ward and bed type: total, occupied (OCCUPIED + DISCHARGE_PLANNED), free, blocked. Running it twice for the same date overwrites. **There is no catch-up**: if the worker was down at midnight that day has no census, and reports say how many days have data. A snapshot taken late would silently misstate midnight, so I left the gap visible.
61. **Reports** (admin only): occupancy (from the census), length of stay, turnover, census history. All take `?from=YYYY-MM-DD&to=YYYY-MM-DD` in hospital-local dates, both inclusive, default the last 30 days, at most 366 days. `GET /api/reports/turnover` is an addition to the spec's three report routes, because the spec's report list names turnover. A patient moved between wards counts in the ward they left from. Average stay is admitted to left; "order to left" is the time from discharge order to the patient leaving, which is the number the spec's pilot baseline asks for. Average cleaning time is CLEANING to FREE from the bed event history.
62. **CSV export has no patient names or phone numbers.** Reports need stay lengths, not identities. `admissions.csv` has UHID (so the hospital can find the stay in its own system), age, sex, ward, bed, every timestamp, outcome and stay length. Cells that a spreadsheet would run as a formula (starting `=`, `+`, `-`, `@`) are neutralised. Every export is written to the audit log.
63. **Retention** runs nightly at 02:30 hospital time. A patient whose every admission ended more than `RETENTION_DAYS` ago, and who is not admitted now, gets name `Anonymised`, UHID `ANON-<id>`, and phone and ABHA number cleared. Age and sex stay so reports keep working. One run is recorded in the audit log with the count. **Not built:** a per-patient erasure button for DPDP "right to erasure" requests, and the printable patient notice. Both are small and fit in Phase 7 with the admin guide; tell me if you want erasure sooner.
64. **Backups** run in a `backup` container (postgres:16 image): `pg_dump` in custom format, encrypted with AES-256-CBC (PBKDF2, 200,000 iterations, random salt) using `BACKUP_PASSPHRASE`, one file a day at 02:30 container time into `./backups`, files older than 14 days deleted. It refuses to run if the passphrase is missing, shorter than 12 characters or still the sample value. Without the passphrase a backup cannot be opened, so keep a copy of it away from the server. `backup/restore.sh` restores into a new scratch database by default so a mistake cannot overwrite live data, and has a `--check` mode. **Backups stay on the same machine** until the hospital copies `./backups` elsewhere (second disk, another PC, cloud storage). The admin guide will say so in capitals.
65. **`.gitattributes`** forces LF line endings on `*.sh`, because a Windows checkout would otherwise break the scripts inside the Linux container.
66. **Idle lock.** After `IDLE_LOGOUT_MINUTES` without a touch the screen is covered. With a PIN set, the user types it to continue; with no PIN, or after five wrong PINs (server limit, 15 minutes), they are logged out. The lock survives a reload (the last-activity time and a locked flag live in the browser's localStorage), so reloading does not bypass it. **Honest limit:** this stops a passer-by at an unattended ward phone. Someone using the browser's developer tools could clear it. The login itself still ends after 12 hours. Real device lockdown belongs to the phone's own screen lock.
67. **Offline queue.** Taps on beds (reserve, admit, status changes, discharge steps, transfer, mark clean) made while the server is unreachable are stored in the phone's IndexedDB with the bed `version` seen, and replayed oldest first when the connection returns (on the browser's online event, on page load, and every 20 s while anything waits). The server's answer decides: success removes it; 409 shows "Bed changed, please refresh" and drops it; 401 keeps everything until the nurse logs in again; other refusals (for example no access) are shown and dropped; network or server errors stop the replay and keep the rest in order. Admin screens are not queued. A replay whose first answer was lost would show a false "changed" message, which is the safe direction.
68. **A bug the browser test found:** a failed refresh while offline makes Next.js fall back to a full page load, which lands on the browser's "no internet" page. All screens now use `safeRefresh()`, which first checks the server is reachable. Verified in a real browser (offline, tap, banner, reconnect, sent; and a stale tap giving the conflict message).
69. **Limit:** the offline queue works for taps made while a page is already open. Opening or reloading a page with no network needs the PWA app shell (service worker), which is Phase 6; Playwright offline tests are Phase 7.
70. **Audit viewer** (`/admin/audit`): newest first, 50 per page, filter by action, person and date. Bed rows show "Ward / Bed label". It holds ids and labels only, never patient names.

## Phase 4

47. **Realtime design.** Every bed change already does `NOTIFY beds` inside its transaction. The app opens ONE Postgres `LISTEN` connection (the `pg` package, since Prisma cannot LISTEN) and fans events out to all open `/api/stream` connections. The listener starts with the first viewer and closes after the last, reconnects with backoff (1 s up to 30 s), and after every reconnect sends a `resync` event so screens reload anything they missed. Measured delivery: a desk reservation reached a viewer's open stream in under 0.4 s (the test asserts under 2 s).
48. **Events hold no patient data**, only bed id, ward id, old and new status, version. That is why `/api/stream` is open to every logged-in role including VIEWER. A test checks a real admission never leaks a name into the stream, and the parser drops unknown fields.
49. **Screens refresh by re-fetching, not by patching.** On an event the page calls `router.refresh()` (debounced 150 ms), so what you see always comes from the server with the right permissions applied. Simplest and cannot drift. A small "Live / Reconnecting" label (word plus symbol, not colour alone) shows the connection state. Ward maps only react to their own ward.
50. **Stream and logins.** The role check runs when the stream opens. A user deactivated afterwards keeps an open stream until it closes, which is acceptable because it carries only ids and statuses; every action and every page still re-checks the user.
51. **Occupancy %** = (occupied + discharge-planned) / (total beds minus blocked). A planned discharge still holds the bed, and a blocked bed is out of service so it is not capacity. Reserved and cleaning beds count as available capacity that is not free yet. A hospital with no usable beds shows "–".
52. **"Discharges today"** = open discharge plans due before the end of today in the hospital's time zone (default Asia/Kolkata), including ones already overdue, since they are still waiting. Time-zone and daylight-saving maths is unit-tested.
53. **Dashboard** is counts only: hospital totals (free, occupancy, discharges today, being cleaned) and a tile per ward with free by bed type. Wards link to the ward map for roles that may open it. A "Full screen" button is for the casualty TV with a VIEWER login. `GET /api/dashboard` returns the same numbers for any logged-in role.
54. **Find a bed** (desk only, as the API table says): filters bed type, patient sex (matches wards of that sex or mixed wards) and ward. Shows free beds grouped by ward with Reserve (one tap), and a "Reserved now" list with minutes left and Cancel. Reservations expire by themselves after `RESERVATION_MINUTES`.
55. **Discharge tracker.** Lists open admissions that have a discharge order, longest-waiting first, with a checklist (order, summary, bill, medicines), "n of 4 steps", and a red border plus the word "Overdue" after `DISCHARGE_ALERT_HOURS`. Nurses see only their own wards, doctors, desk and admins see all (it contains names). Doctors and nurses can tick steps and confirm "Patient left" (two taps). Desk and admin are view-only, matching the API table. Admissions with a plan but no order yet are on the ward map, not here.
56. **Housekeeping list**: beds in CLEANING, oldest first, with a large one-tap "Mark clean". Shows bed and ward only, never patients. Housekeeping can clean any ward; a nurse only her own; admin is view-only.
57. **Checklist ticks** now also send a notify (marked `checklist`) so the tracker updates for everyone, even though the bed status does not change.
58. **Navigation** shows only the screens a role can use: Find a bed (desk), Discharges (nurse, doctor, desk, admin), Housekeeping (housekeeping, nurse, admin), Admin (admin).
59. **Needs a proxy setting if you add one.** Behind nginx or Caddy, response buffering must be off for `/api/stream` (the app sends `X-Accel-Buffering: no`; Caddy streams by default). Noted for the Phase 7 admin guide.

## Phase 3

35. **Who may do which move** follows the section 4 table literally, including its ambiguous first row, which I read as: FREE to RESERVED and to OCCUPIED by DESK or NURSE, FREE to BLOCKED by NURSE or ADMIN. The API table is stricter for reserve (`POST /reserve` is DESK only), and the route enforces that. Doctors are not limited to wards (only nurses have ward assignments). ADMIN can block and unblock but cannot admit or discharge, as the API table says.
36. **Every change checks `version` first.** A stale client always gets `409 VERSION_CONFLICT` with the text "Bed changed, please refresh", even when the real cause is that the bed was taken. Without this a losing racer sometimes saw "invalid move" and sometimes "changed", depending on timing. Version is required on every bed action.
37. **Concurrency** is enforced by one conditional `UPDATE ... WHERE id AND version AND status`, so exactly one of two simultaneous writers matches and the other rolls back completely (no half-created patient). Transactions wait up to 15 s for a connection (Prisma's 2 s default made losers fail with a database timeout instead of a clean 409).
38. **Admitting:** a UHID can only have one open admission, enforced with a Postgres advisory lock so two beds cannot admit the same patient at once. If the UHID already exists the patient record is reused and updated. Patient sex is **not** matched against ward gender; the desk filters by gender in Find a bed (Phase 4) and blocking a legitimate admission (newborn, emergency) is worse than allowing a mismatch.
39. **Discharge flow.** Steps: plan, order, summary, bill, meds, left. Giving the **order** also plans the discharge (one tap for the doctor). Summary, bill and meds need the order first and can be un-ticked. **Left** frees the bed into CLEANING and closes the admission; a normal discharge needs the order, but LAMA, REFERRED and DIED do not. "Patient left" cannot be undone. Cancelling a plan clears its checklist. Checklist ticks are audit-logged but are not bed status changes, so they do not bump `version` or write a BedEvent.
40. **Transfer** is nurse-only, from an OCCUPIED bed (not DISCHARGE_PLANNED: cancel the plan first) to a FREE bed, any ward. The old bed goes to CLEANING, the new one OCCUPIED, a `BedTransfer` row is written. The nurse must be assigned to the source ward.
41. **Block** needs a reason, shown on the bed. Cancelling a reservation and un-blocking go through `POST /status`.
42. **Reservation auto-release** runs in the worker every minute and records a BedEvent with no actor ("reservation expired"). A reservation with no deadline counts as expired so it cannot stick.
43. **Names on the ward map.** Shown to admin, desk, doctor and nurses assigned to that ward. A nurse from another ward sees the beds and statuses but no patients and no actions. Housekeeping and viewers cannot open ward maps (`/wards/:id`); they see counts only. The dashboard, still a placeholder until Phase 4, shows counts only.
44. **`NOTIFY beds`** is sent inside each change transaction (delivered on commit) with only ids and statuses, no patient data. Nothing listens yet; the SSE fan-out is Phase 4.
45. **Integration tests need a real Postgres.** `npm test` (unit, 456 tests, no database) is separate from `npm run test:integration` (19 tests: the concurrency test, journey, transfer, roles, expiry). Setup is in the README. CI wiring is Phase 7.
46. **Not yet in the UI:** offline queue and replay (Phase 5), live refresh (Phase 4: for now screens refresh after your own action), Hindi (Phase 6). The ward map was verified through the API and page rendering, not clicked through in a browser.

## Phase 1

1. **Spec filename.** The file in the folder is `Spec.md`, not `SPEC.md`. Left as is (Windows is case-insensitive). Rename it before cloning on Linux.
2. **Single hospital per install.** The data model in section 4 has no `hospital_id` on other tables, so one install serves one hospital. The `Hospital` table holds one row.
3. **Tailwind v4 + hand-written shadcn-style components.** Tailwind v4 (CSS-first, `@tailwindcss/postcss`) instead of v3. shadcn/ui components are added by hand in `src/components/ui` (card, badge) with the same API and `components.json`, because the CLI is interactive. More are added as screens need them.
4. **Prisma 6 pinned (`^6`).** Prisma 7 changes client generation and config; 6 is the stable, widely documented choice.
5. **Prisma table names** use the snake_case names from the spec (`@@map`), so SQL and CSV exports match section 4.
6. **`bcryptjs`** (pure JS, cost 12) instead of native `bcrypt`, to avoid native build problems on Windows and Alpine.
7. **Dockerfile** is a single simple image (Node 20 slim, dev dependencies kept) used by both `app` and `worker`. This lets `docker compose exec app npx prisma db seed` work, and the worker run with `tsx`. Image size is not optimised.
8. **Migrations on start.** The `app` command runs `prisma migrate deploy` before `npm start`. The worker waits for the app to be healthy, so the schema exists first.
9. **Compose `POSTGRES_PASSWORD`.** `.env.example` has a `POSTGRES_PASSWORD` (not in the spec table) so the db and `DATABASE_URL` use one password. Compose builds `DATABASE_URL` from it.
10. **Backup service and Caddy** are not in Phase 1 (spec puts backups in Phase 5, HTTPS as optional).
11. **Worker** is a heartbeat only in Phase 1. Real jobs come in Phase 5.
12. **Demo seed** is skipped if a hospital row exists, so re-running never duplicates or deletes data. Demo users share the password `bedboard123` and phones `9000000001` to `9000000006` (admin, nurse, desk, doctor, housekeeping, viewer). Demo only. Change or delete before real use. Patient names in the seed are made up.
13. **Seed mix.** About 75% of beds occupied, 10 of them with a pending discharge order (3 older than 4 hours so they show red), plus a few cleaning, blocked and reserved beds so every status appears.
14. **Health page** (`/health`) shows counts by status only and database connectivity. `GET /api/health` is public and returns no data beyond up or down.
15. **Landing page** at `/` is a placeholder until Phase 6.
16. **Phone-only login number format** is not validated in Phase 1 (no auth yet). It will be 10-digit Indian mobile numbers in Phase 2.
17. **State machine tests.** The "tests first" rule applies to `src/lib/beds.ts`, which is Phase 3. Phase 1 has no state machine code. Vitest is configured and `tests/unit` is ready.
